# PDF Hail Report — Handoff (filename + date accuracy)

Written 2026-07-15, to be picked up in a fresh session. Two issues reported by James on the
hail damage PDF (`GET /Leads/{id}/Report`, generated by `Services/HailReportService.cs` from
`Controllers/LeadsController.cs`).

## Issue 1 — Filename doesn't reflect the address

`Controllers/LeadsController.cs:359`:

```csharp
var filename = $"HailReport-{lead.Id}-{DateTime.Now:yyyyMMdd}.pdf";
```

Downloaded files are named e.g. `HailReport-42-20260715.pdf` — just the internal lead ID and
today's date, nothing address-identifying. James wants the filename to reflect the property
address instead (e.g. `HailReport-123-Main-St-20260715.pdf` or similar — exact format TBD).

`lead.Address` is already in scope at that point in the method (used throughout, e.g. line 156
in HailReportService for the report body itself). This is a small, contained fix: build a
filesystem-safe slug from `lead.Address` (strip/replace characters invalid in filenames — commas,
slashes, etc.) and splice it into the filename. No architectural questions here, just needs the
slugging logic written and a decision on exact format.

## Issue 2 — Report dates don't reflect the actual storm dates for that address

This one has a real root cause, not just a formatting fix. There are **two independent, disagreeing
sources of storm-date truth** in the report:

**Source A — the summary box** (top of the PDF: Risk Level, Hail Size, Storm Date). Rendered in
`Services/HailReportService.cs` lines 86–87:

```csharp
var hailSizeText = lead.HailSize ?? "Not recorded";
var stormDate    = lead.LastStormDate ?? "Not recorded";
```

These come straight off the `Lead` entity's stored columns (`RiskLevel`, `HailSize`,
`LastStormDate` — see `Data/Models/Lead.cs`). Those columns were populated **once, at save time**
— whenever the lead was originally created (via `/RoofHealth/SingleAddress`, the neighborhood
scan, or the Storm Explorer click-to-add/draw-area features added this session). They never get
refreshed after that.

**Source B — the detailed hail-history table** further down the PDF. This is built from a
**live, fresh query** run at report-generation time, in `Controllers/LeadsController.cs` lines
241–299: it calls out to SWDI, Mesonet LSR, NOAA Storm Events, and Tomorrow.io in parallel, then
filters to events within `display = 10.0` miles of `lead.Lat`/`lead.Lng` (see the comment at line
262–263 — this radius was deliberately widened from 2 miles earlier because rural storm reports
log at the nearest town). This list can easily contain different dates than Source A, especially
if:
- the lead was saved a while ago and newer storm data has since become available (NOAA has a
  ~90–120 day radar lag that Tomorrow.io is meant to fill),
- or the original save used a different/narrower radius or data source mix than what `Report()`
  queries now,
- or the address's stored lat/lng drifted from what was used originally (e.g. a geocode retry).

So: the box at the top says "Storm Date: March 3, 2026" (whatever was true when the lead was
saved), while the table below it might show a completely different most-recent date from the live
10-mile-radius query. That mismatch is almost certainly what James is seeing.

**This is the same category of bug already found and fixed once this session**, for a different
feature: Storm Explorer's click-to-add-lead originally saved bare `{address, lat, lng}` with no
storm data at all, causing "Not recorded" everywhere — fixed by calling `/RoofHealth/SingleAddress`
before saving so the lead carries real data. This is the same root issue one level further down:
even when a lead *does* carry real data at save time, nothing keeps it in sync with what a fresh
query would say later.

### Questions for the next session to resolve before fixing

1. **Should the PDF's summary box re-run the live 10-mile query and use *that* for Risk
   Level/Hail Size/Storm Date, instead of trusting `lead.RiskLevel`/`HailSize`/`LastStormDate`?**
   This would make the summary and the detail table always agree, but changes what "Risk Level"
   on a saved lead means (it'd only be accurate at report-generation time, not save time) — worth
   discussing whether the Saved Leads table's Risk badge should also be refreshed at that point,
   or left as a "snapshot at save time" value with the PDF being the "current" view.
2. Alternatively, **should the live query's summary values get written back to the `Lead` row**
   whenever a report is generated, keeping the saved lead's fields in sync going forward? Simpler
   mentally, but means the Saved Leads table's data changes as a side effect of downloading a PDF.
3. Either way, double-check whether the 10-mile `display` radius is actually appropriate for the
   *summary* stat (most severe/most recent single hail size) vs. the detail table (list of every
   event) — those may reasonably want different radii.
